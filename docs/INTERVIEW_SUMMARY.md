# Sundry 架构演进与面试讲解版

> 单商户自营电商，实物 + 数字商品。
> 技术栈：Spring Boot 4.1.1 / JDK 17 / MyBatis / Flyway / MySQL 8.0 / Redis / Kafka / MinIO / Vue 3 + Vite + TS + Pinia。
> 测试：131 个集成测试全绿。压测：200 用户抢 50 件，p99 139ms，零超卖、零重复。

---

## 1. 一句话介绍

从零实现了一个可完整跑通的单商户电商系统：认证权限、商品与文件、购物车与地址、下单支付履约、退款退货，以及一套完整的秒杀高并发方案。

## 3. 秒杀链路

```
客户端
  │
  ├─ Redis 固定窗口限流（每用户每秒 5 次）
  ├─ 活动/商品/地址校验
  ├─ Redis Lua：判重 + 判库存 + 扣减 + 标记用户（原子）
  │     失败：售罄 / 限购 / 未就绪
  └─ 成功：投 Kafka，返回 requestId（202）
                │
                ▼
        消费端幂等建单
          ├─ 活动 sold_count +1（条件更新）
          ├─ 实物商品扣库存（条件更新）
          ├─ 写订单 + 订单项
          └─ 写 Redis 结果 + 加入 ZSET 延迟队列
                │
                ▼
        前端轮询结果：PROCESSING / SUCCESS / FAILED
```

### 关键设计

- **防超卖**：Redis Lua 原子扣减是第一道闸门；数据库条件更新是最后一道防线。
- **一人一单**：Lua 里的购买者 Hash + 数据库唯一索引 `(activity_id, user_id)` 双保险。
- **失败补偿**：投递失败、建单失败都会回补 Redis 库存并移除购买标记；重复消息命中唯一索引时返回已有订单。
- **超时关单**：Redis ZSET 存支付截止时间，Lua 原子领取到期订单；数据库定时扫描做兜底。
- **懒预热**：Redis key 丢失时，按 `stock - sold_count` 和订单表购买者重建，`SETNX` 防止并发重复预热。
- **对账**：核对 `sold_count`、有效订单数、Redis 剩余库存；只有已售数一致时才允许按 DB 修复 Redis。
- **可观测性**：Micrometer + Prometheus，记录提交结果、建单成功/失败、补偿次数、提交耗时。

## 4. 缓存链路

```
Caffeine（本地）
   │ miss
   ▼
Redis
   │ miss
   ▼
MySQL
```

- **击穿**：本地分段锁 + Redis `SET NX` 互斥重建，只允许一个请求回源。
- **穿透**：商品详情不存在时缓存空值 60 秒。
- **雪崩**：Redis TTL 加随机抖动，避免同一时刻批量过期。
- **降级**：Redis 异常时直接读 DB，不阻断商品浏览。
- **列表缓存**：只缓存商品 ID + 总数；卡片按商品单独缓存。
  - 商品改名/改价：只失效单张卡片，不升级列表版本。
  - 新增/删除/上下架/换分类：列表版本号 +1，旧 key 靠 TTL 过期。
- **库存展示**：允许最多旧 60 秒；下单和秒杀仍以 DB/Redis 校验为准。

## 5. 一致性设计

| 场景 | 手段 |
|---|---|
| 下单扣库存 | 事务 + 条件更新 `stock >= ?` |
| 商品创建重试 | `Idempotency-Key` + 数据库唯一索引 |
| 秒杀一人一单 | Redis 购买者标记 + 唯一索引 `(activity_id, user_id)` |
| 订单状态流转 | 带前置状态的条件更新，重复调用幂等 |
| 退款/退货 | 状态机 + 条件更新 + 审核流水 |
| 消息重复消费 | 结果状态检查 + 唯一索引 |
| 缓存与 DB | 有界最终一致（≤60 秒），交易路径不走缓存 |
| 订单号 | 雪花算法，41 位时间 + 10 位 workerId + 12 位序列 |

## 6. 六个可展开讲的技术点

### 6.1 从 DB-only 到 Redis 秒杀

- 最初下单完全靠数据库条件更新，正确但不适合突发流量。
- 秒杀引入 Redis 库存计数器 + Lua 原子脚本，把无效请求挡在 DB 之前。
- 数据库仍然保留条件扣减，Redis 丢数据或脚本异常时不会超卖。

### 6.2 为什么不用分布式锁防超卖

- 按 SKU 加分布式锁会把同一商品的所有请求串行化，吞吐被锁持有时间限制。
- 单 key 的“判断 + 扣减”用 Lua 本来就是原子的，不需要锁。
- 分布式锁保留给预热、对账这类跨实例的复合操作。

### 6.3 缓存失效粒度优化

- 第一版列表缓存整页快照，任何商品变更都要升级全局版本，热门列表整体重建。
- 改成“ID 页 + 卡片独立缓存”：
  - 普通编辑只失效一张卡片；
  - 只有成员变化（新增/删除/上下架/换分类）才升级版本号。
- 代价是首次列表请求要逐张取卡片，但卡片命中本地缓存后成本很低。

### 6.4 Kafka 异步建单与补偿

- 同步建单在峰值时 DB 连接池容易成为瓶颈，改为 Lua 预占后投 Kafka。
- 接口立即返回 `requestId`，前端轮询结果。
- 投递失败：立即回补 Redis。
- 建单失败：回补库存、移除购买标记、写失败原因。
- 重复消费/唯一索引冲突：返回已有订单，并归还多扣的库存。

### 6.5 超时关单

- 不用 Redis key 过期事件：过期是惰性删除，事件不持久化，可靠性不够。
- 用 Redis ZSET + Lua 原子 `ZRANGEBYSCORE + ZREM` 领取到期订单，多实例不会重复处理。
- 数据库定时扫描保留做兜底；两者都靠条件更新保证只回补一次。

### 6.6 压测与验证

- k6：200 个不同用户并发抢 50 件数字商品。
- 第二轮（Kafka producer 预热后）：p99 139ms，短时吞吐约 2000 req/s，0 个意外状态。
- 一致性校验：
  - `sold_count = 50`
  - 订单 50 行、50 个不同用户
  - Redis 剩余库存 0、购买者 50
  - 补偿次数 0
- 第一轮 p99 1.16s，定位为 Kafka producer 首次初始化，预热后恢复。

## 8. 高频追问

**Q：Redis 扣了但建单失败怎么办？**
A：投递或建单失败都会回补 Redis 库存并移除购买标记，同时写失败结果；对账任务兜底。重复消息和唯一索引冲突会返回已有订单并归还多扣库存。

**Q：为什么不用 Redis key 过期来关单？**
A：过期事件是惰性删除 + pub/sub，不持久化，服务重启和主从切换会丢事件。用 ZSET 延迟队列或 MQ 延迟消息更可靠。

**Q：一人一单怎么保证？**
A：Lua 中原子检查并写入购买者 Hash；数据库唯一索引 `(activity_id, user_id)` 兜底。取消后保留购买标记，按业务规则不允许重复抢。

**Q：雪花算法要注意什么？**
A：workerId 全局唯一；时钟回拨超过 5ms 直接拒绝；64 位 ID 超过 JS 安全整数，订单号按字符串输出。

**Q：缓存和库存怎么保证一致？**
A：展示层接受有界最终一致（≤60 秒）；交易层完全不信任缓存，Redis 和 DB 条件更新才是权威判断。

**Q：为什么选 Kafka 而不是 RocketMQ？**
A：后续有 CDC/数据管道规划，Kafka 生态更合适；超时关单用 Redis ZSET 补足 Kafka 没有原生延迟消息的短板。

**Q：这个方案的局限？**
A：单机压测不等于生产容量；消费端失败不重投，瞬时 DB 故障会让本次抢购失败并回补；单 key 库存未分桶；支付仍是模拟；没有部分退款和退货运费建模。
