## 1. 退款金额重复累计

**现象**：一笔 100 元退款、2 条商品明细，报表算出 200 元。

**根因**：`semantic-layer.yml` 的 base 无条件 JOIN `order_item`；`refund_summary` 是订单粒度，退款行被每个明细复制一次，`SUM(r.refund_amount)` 重复累计。

**修复**：

- `refund_amount` 按明细数量分摊：`SUM(r.refund_amount * oi.quantity / 订单总数量)`，多明细汇总回订单金额。
- 退款指标不允许按 `category` / `product` / `product_type` 拆分，避免“把整笔退款摊到每个分类”的错误口径。
- 校验错误返回 `INCOMPATIBLE_PAIR`。

**测试**：

- `Nl2sqlQueryIntegrationTest#refundAmountDeduplicatesOrderItemsAndRateUsesPercent`
- 一笔 2 明细、退款 100 的订单，断言 `refund_amount = 100`
- 退款金额 + `category` 断言 400

## 2. 退款率单位错误

**现象**：实际 50% 显示为 `0.5 %`。

**根因**：表达式返回 0~1 比例，`unit` 写成 `%`，前端直接拼单位。

**修复**：表达式乘 `100.0`，与 `%` 单位一致。

**测试**：2 单 1 退款，断言 `refund_rate = 50.0`。

## 3. 秒杀建单后 Redis 失败错误回补

**现象**：DB 订单已提交，Redis 超时队列/结果写入失败，代码回补库存并标记 FAILED。

**根因**：`transactionTemplate.execute` 提交后，`timeoutService.add` / `resultService.success` 与建单放在同一个 `try`；异常进入 `failAndRollback`。

**修复**：

- 新增 `recordPostCommit`：DB 提交后的 Redis 副作用单独 `try/catch`，失败只记日志，**不回补库存、不标记失败**。
- 结果查询增加 DB 兜底：Redis 状态为 `PROCESSING` 时，查 `orderMapper.findSeckillOrder(userId, activityId)`，存在订单直接返回 SUCCESS。
- DB 超时扫描仍是关单兜底。

**测试**：

- `SeckillOrderServiceTest`：`timeoutService.add` 抛异常，断言 `rollbackReservation` / `resultService.fail` 从未调用，`resultService.success` 仍执行。
- `SeckillResultServiceTest`：缓存 PROCESSING、DB 有订单时返回 SUCCESS。
- `SeckillOrderIntegrationTest` 23 个用例通过。

## 4. 文件入库后完成态缓存失败

**现象**：文件记录已写入，完成态缓存失败后对象被删，DB 留下指向不存在对象的记录；缓存过期后重试也无法找回文件。

**根因**：

- `complete` 把 `fileObjectMapper.insert`、`cacheDone` 放在同一个 `try`，`catch` 删除对象，但不回滚 DB。
- 完成态缓存 1 小时过期，上传会话已删，重试无法恢复 `fileId`。

**修复**：

- 只有 `fileObjectMapper.insert` 失败才删对象。
- 入库成功后 `cacheDone` 失败只记日志，不删对象/记录。
- 新增 `findByObjectKey`：完成请求重试时按对象 key 找回已入库记录，不依赖 Redis 完成态缓存。
- 孤儿清理逻辑保持不变（软删除过期 + 长期无引用），但完成态丢失不再直接导致对象被删。

**测试**：

- `DigitalUploadIntegrationTest#completeIsIdempotentWhenDoneCacheExpires`：删除 done/state 缓存后再次 complete，返回同一个 fileId，对象仍在。
- `DigitalUploadIntegrationTest` 17 个、`FileCleanupIntegrationTest` 6 个通过。

## 5. 换账号残留助手聊天内容

**现象**：同一标签页退出 A、登录 B，助手仍显示 A 的订单卡片、购买汇总、经营分析内容。

**根因**：

- `AssistantWidget` 在 `App.vue` 只挂载一次，`entries` 是组件状态。
- logout 只清 token/user，没有清 `entries` / `open` / `sessionId`。
- `sessionStorage` 的 assistant sessionId 不区分用户。

**修复**：

- 监听 `auth.user?.id`，变化时清空 `entries`、关闭面板、按用户生成 sessionId：
  `assistant:${userId ?? 'anon'}`。
- 换账号后不会复用上一个账号的会话 key。

**验证**：

- `npm run build` 通过。
- 手工路径：退出 → 登录另一账号 → 助手列表为空、面板关闭。

## 6. 向量同步恢复缺口

**现象**：MySQL 向量记录先更新，Milvus 写入失败后，定时扫描认为已同步，不再重试。

**根因**：

- `embedAndStore` 先 `embeddingMapper.upsertBatch`，再 `milvusClient.upsert`。
- Milvus 失败时 MySQL `updated_at` 已刷新；`findStaleProducts` 条件 `e.updated_at < p.updated_at` 不再命中。

**修复**：

- 调整顺序：先写 Milvus，成功后再更新 MySQL。
- Milvus 失败时 MySQL 保持旧时间/缺失，下一轮 `syncStale` 会重新处理；Milvus upsert 幂等。
- 若 Milvus 成功、MySQL 失败，MySQL 仍是旧的/缺失，也会被下一轮重试。

**测试**：

- `ProductEmbeddingServiceTest#milvusFailureDoesNotAdvanceMysqlUpdatedAt`：Milvus 抛异常，断言 `embeddingMapper.upsertBatch` 从未调用。

## 遗留

- 退款金额按明细数量分摊，是“订单级退款”的一种归因假设；如果业务要求按金额分摊，需要改成按 `oi.price * oi.quantity` 权重。
- 文件完成态缓存丢失后能按对象 key 恢复，但对象 key 仍需客户端保留；更彻底的做法是把 uploadId → fileId 落库。
- 秒杀结果缓存写失败时，轮询切到 DB 兜底；如果 Redis 整体不可用，轮询仍会失败。
